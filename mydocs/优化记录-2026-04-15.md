## 修复内容总览

### ✅ 高优先级问题（已全部修复）

#### 1. Session 扫描并行化
**问题**: 串行处理文件导致大规模场景下性能瓶颈  
**修复**: 
- 添加文件级并行处理，使用线程池（默认 10 并发）
- 参考健康检查的并行模式实现
- 添加超时控制（30 分钟）和资源清理逻辑

**代码位置**: `SessionScanTask.executeScan()` 方法（第 944-987 行）

---

#### 2. Turn 聚合逻辑完整性
**问题**: 文件最后一组消息可能永远不会被写入数据库  
**修复**: 
- 在 `streamProcessAndBatchWrite` 方法末尾添加剩余 Turn 处理逻辑
- 确保最后一个未完成的 Turn 也能被正确写入

**代码位置**: 第 1213-1220 行

---

#### 3. Token 实时同步策略（方案B - 优化版）
**问题**: Token 数据获取时机不明确，原设计为每个 session 单独调用 RPC  
**修复**: 
- 明确采用方案B：实时同步，但优化为**一次性获取整个 instance 的所有 session Token 数据**
- 通过源码确认 `sessions.list` API 返回 session 列表，每个 session 包含完整 Token 统计
- 每个 instance 只调用一次 `sessions.list`，而非每个 session 调用一次
- 添加去重逻辑：使用 `ConcurrentHashMap` 记录已同步的 instance，避免重复调用
- 新增 `fetchAllSessionTokenStats()` 方法，批量获取所有 session 的 Token 数据
- 新增 `shouldSyncToken()` 方法判断是否需要同步

**代码位置**: 
- `processSessionFile()` 第 1144-1157 行
- `syncTokenData()` 第 1292-1332 行
- `fetchAllSessionTokenStats()` 第 1800-1846 行
- `shouldSyncToken()` 第 1173-1179 行
- 使用场景说明：第 1893-1920 行

**性能提升**：
- 原设计：1000 个 session = 1000 次 RPC 调用
- 优化后：1000 个 session = 1 次 RPC 调用
- RPC 调用次数减少 99.9%

**代码位置**:

#### 5. 事务边界明确
**问题**: 批量写入的事务策略不清晰  
**修复**: 
- 在性能优化建议中明确：每个批次（100 条 Turn）作为一个独立事务
- 使用 `ON DUPLICATE KEY UPDATE` 实现幂等性
- 失败时仅回滚当前批次，不影响其他批次

**文档位置**: 第 1970-1973 行

---

#### 6. 异常恢复机制
**问题**: 缺少断点续传和重试机制

- 说明基于 `last_message_id` 的断点续传机制
- 定义重试策略和幂等性保证
- 连续失败 3 次的文件标记为异常并告警

**文档位置**: 第 1986-1997 行

## 优化效果预期

### 性能提升
- **Session 扫描速度**: 从串行 33 分钟（1000 文件）降低到并行 3-5 分钟
- **Compaction 检测**: 减少一遍完整扫描，I/O 开销降低约 50%

### 可靠性提升
- **数据完整性**: 最后一个 Turn 不再丢失
- **断点续传**: 任务中断后可从上次位置继续
- **容错能力**: Gateway 不可用时不影响扫描进度

### 可维护性提升
- **代码清晰度**: 事务边界、异常处理策略明确
- **文档完整性**: 补充错误响应格式，修复格式问题
